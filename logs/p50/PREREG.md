# P50 phase 2 pre-registration — the per-instance release-offset compensation

Written 2026-10-27, **before** the phase-2 code exists and before any compensated
run. The measurement it rests on is `logs/p50/OFFSET_TABLE.md` (phase 1, same
tree: HEAD `3a8a581`, `fruits.py` `dff684b1`, no `src/`/`configs/` change). The
lane is `.slim/deepwork/p50-release-offset.md`.

## 1. The question, and what is already measured

**Does compensating the release offset at `respawn` put the *delivered* lateral x
inside the 0.18-0.39 catch band without costing placements or acquisitions?**

Measured in phase 1 (do not re-derive):

* `delivered x = spawn x + offset(instance)`, with the transport contributing
  **0.00 mm** (P38, re-confirmed on the delivered path: 0.09 mm over 215-224
  ticks);
* the offset is a **per-instance constant** at a fixed initial condition: two
  passes over 48 cells bit-identical (spread **0.00 mm**), a 3-repeat cell
  `-2.90 / -2.90 / -2.90 mm`, cross-process/cross-window agreement ≤ 0.15 mm;
* it is **x-independent for 13/16 instances** (≤ 0.5 mm over the whole 0.16 m
  band) and, for the three rolling instances, a choice among **1-3 discrete
  modes** 11-20 mm apart (not a slope);
* in the **shipped line** (release-attributed, 65 releases) the table matches
  **55/65 releases to ≤ 0.5 mm and 60/65 to ≤ 2 mm**, max 18.2 mm (one kiwi's two
  modes);
* **it cannot be a (species, diameter) table**: two strawberries 0.9 mm apart in
  diameter differ by **44.3 mm**; a pooled fit leaves a residual sd of 10.19 mm
  and a max residual of 31.0 mm; a fresh seed draws a new instance set
  (`-8.4 .. +34.8 mm`). **So the table must be per pool.**
* **the arithmetic**: uncompensated `U(0.20, 0.36)·+offset` delivers **0.35 %**
  below 0.180 and **0.56 %** above 0.390 (min 0.173, max 0.400); compensated at
  one x: **0.00 % / 0.00 %** (min 0.199, max 0.365); paired on the 65 actual live
  draws, 1.54 % below 0.20 and 3.08 % above 0.36 both go to **0**;
* **the pear pool has no release tail** (`-3.33 .. +2.69 mm`, 0.00 % outside the
  band before and after).

## 2. The compensation (the knob)

`FRUIT_RELEASE_OFFSET` (**default `0`**), read once at import in
`fruit_sorting/fruits.py`, applied inside `respawn`:

```
planned = rng.uniform(x_min, x_max)          # unchanged draw, unchanged stream
x_spawn = planned - offset(instance) / 1000  # only when the knob is on
```

* **`FRUIT_RELEASE_OFFSET_TABLE=<path>`** (JSON, default none). With the knob on
  and no table the run **refuses to start** (a silent no-op would be a false
  measurement).
* **The table** is `{signature: offset_mm}` with `signature = "<species>|<dia to
  0.1 mm>"` — the instance identity that the pool exposes. A signature that is
  missing, or an entry whose signature does not cover the pool, is counted
  (`offset_table_misses`) and that instance is left **uncompensated** (the raw
  draw). The table is generated by a **live probe run at the arm's own seed**
  (`offset_probe.py FRUIT_OFFSET_MODE=live`, 240 s), whose per-instance value is
  the **mean of that instance's attributed releases**.
* **The mode rule**: if an instance's live releases show ≥ 2 clusters separated
  by **> 5 mm**, its table value is the **midpoint of the two extreme modes**
  (minimax). At seed 5 that is kiwi idx 02 only (`+35.0 / +39.7 / +54.5 / +54.6`
  → `+44.8`, worst residual 9.8 mm instead of 19.5). Measured basis:
  `OFFSET_TABLE.md` §4.
* **The scope gate**: the compensation is applied **only when the supply is
  single-file** (`not supply.patch and not supply.bed`). The reason is measured,
  not assumed: a patch/bed pair is abreast at 0.085-0.12 m, and a per-instance
  lateral shift of up to ±55 mm changes that separation. A skipped release is
  counted (`offset_scoped_off`).
* **The stage/build calibration is *not* the registered form.** It costs 16 × 200
  ticks = **26.7 s** of extra sim at startup (`last_step_motion_tick ≤ 137`), it
  shifts the absolute release schedule (a different branch by construction), and
  a ladder form is only legal for 14/16 instances (§6). It is kept as the
  fallback **only if a fresh seed must be run without a probe first**, and it must
  then pre-register its own battery.
* **Unset contract**: with the knob unset, no table is read, no draw changes, no
  line is added — the tree is byte-identical. Proven by the no-harm arm (§4 M4),
  not asserted.

**Why the draws stay controlled**: the compensation post-processes the value
`respawn` already drew, so the **O arm sees the same planned-x sequence as C**.
That is checked explicitly (M1b) so the A/B compares the *same supply draws* and
only the physical x differs.

## 3. The arms

One claim. Five runs plus one probe, all interleaved in one session, the same
seed (5) and the same policy seed where a policy is involved (none here).

| arm | scenario | env | what it is for |
| --- | --- | --- | --- |
| **M1-C** | the probe, `isolated`, 16 instances × 3 planned x × 2 passes | `FRUIT_RELEASE_OFFSET=0` | the control's delivered-x cells (the measured 4/48 outside the band) |
| **M1-O** | the same probe | `=1` + the seed-5 table | the mechanism endpoint: 0 cells outside the band |
| **M1b** | the probe, `live`, 60 s | `=0` then `=1` | the **planned-x sequences must be identical** (the supply is controlled); plus the live residual |
| **M2-C / M2-O** | the shipped acceptance, `SEED=5`, 10 attempts | `=0` / `=1` | the placed, the acquisition rows, `s/attempt`, the motion gate, the delivered-x rows |
| **M3-C / M3-O** | the pear, `SEED=5 FRUIT_SUPPLY_SPECIES=pear`, 10 attempts | `=0` / `=1` | the inertness control (the pear's offset is ≤ 3.3 mm) |
| **M4** | the acceptance with the env **unset** | — | no-harm: `[fruit]`-identical to the same-batch C **and** to `logs/p44/p2/accept_s5_C.log` (387 `[fruit]` lines, 6/10, 15.0 s/attempt) |

The table for M1-O/M2-O/M3-O is generated **before** the battery by the live probe
at the matching seed and supply (`SEED=5`, and `FRUIT_SUPPLY_SPECIES=pear` for
M3), and its JSON is frozen and md5-pinned in the phase-2 record.

## 4. The endpoints

**P1 — the delivered x (primary, mechanism).** M1-O: the delivered x
(`x_settle`) must be inside `[0.180, 0.390]` in **96/96 cells** (16 × 3 × 2)
against the control's **88/96** (4/48 per pass outside: kiwi idx 02 @0.36 →
0.3998, kiwi idx 13 @0.36 → 0.4131, strawberry idx 05 @0.20 → 0.1780, orange
idx 10 @0.20 → 0.1730). The M2/M3 delivered-x rows (`wait step=0 fruit_x=` plus a
run-neutral `[offset] release planned=.. spawn=..` row in both arms) are
**reported with their exposure** — 10 attempts ≈ 18 releases carries ~0.1 tail
events at the measured rate, so **the arm-level tail share is not a gate** (P38
§3's power statement applies unchanged).

**P2 — the acquisition class does not rise.** Over M2-C vs M2-O: the count of
`dynamic catch-up: residual` rows **above the 6 mm tolerance** (P47/P48: 8/8 of
those are no-grasp) and the count of `no grasp` terminals must be **≤ C**.

**P3 — the placed is non-inferior.** The gate is **M2-O's `[stats] successes ≥
M2-C's**, with two caveats reported beside it: the branch is *moved* by
construction (the spawn x changes, so the fruit sequence does), so the count is
**not** a rate (AGENTS §2); and F3 names the gross case (`O ≤ C - 3` on ten
attempts) separately, so a 1-2 placement slip fails P3 without being read as a
mechanism. `s/attempt` (the `[stats]` line) must be **≤ +5 %** of C.

**P4 — no new failure reason.** The digit-normalised reason set
(`113_rl_report.reasons`) of O must be a **subset** of C's plus the recorded
baseline set; any new key fails.

**P5 — the motion gate.** `scripts/accept.sh`'s gate on both arms: every leg
inside its speed budget, the carry cone reported. **The fingerprint**
(`configs/motion_reference.json`, `8a399626`) is required to match on **M4 only**
(the unset path); the O arm's branch is deliberately different, and a new
reference is recorded **only** if the lever is adopted (phase 3), per the
P40/P41/P42 precedent.

**P6 — inertness on the pear.** M3's two arms may differ only through the branch
the spawn shift creates: `[stats] successes` within the P3 guard, no new reason,
and the delivered-x rows inside the band in **both** arms (the pear's predicted
state).

## 5. The decision rule

Adopt **only if** P1 ∧ P2 ∧ P3 ∧ P4 ∧ P5 ∧ P6 all pass; otherwise **not adopted**,
published as a negative with the mechanism named. A pass is not an adoption by
itself: the flip needs phase 3's commits, the reference re-record (if the
acceptance branch moves) and the docs.

## 6. The falsifiers (each one kills the phase, pre-registered)

| # | falsifier | the measured basis it is set against |
| --- | --- | --- |
| **F1** | the table does not hold: any instance's live mode spread is **> 20 mm**, or the live residual exceeds the band margin | measured at seed 5: 18.2 mm (kiwi idx 02, two modes); at seed 6: 19.4 mm. 20 mm is the margin `[0.20, 0.36] ⊂ [0.18, 0.39]` |
| **F2** | the tail does not fall: **any** M1-O cell outside `[0.180, 0.390]`, or the compensated M2 delivered-x share not below C's | P1 |
| **F3** | the placed regresses: `O ≤ C - 3` (ten attempts) | P3 |
| **F4** | a new failure reason appears | P4 |
| **F5** | no-harm is broken: the env-unset acceptance is not `[fruit]`-identical to `logs/p44/p2/accept_s5_C.log`, or `selfcheck.sh` fails | M4 |

**F1 is the one this phase is most exposed to**: kiwi idx 02 is bimodal *in the
line* (two releases at +54.6, one at +35.0, one at +39.7, at nearly the same x).
The mode rule (§2) halves that to 9.8 mm, but if a longer live run shows the
population is not two-mode but continuous, the table's premise fails and no
midpoint helps.

## 7. Power and exposure

* **M1 is the powered endpoint** (96 cells, 100 % instance coverage, a
  deterministic instrument): 4/48 outside the band per pass is a 100 %-incidence
  mechanism read at the cell level, not a rare-event sample.
* **M2/M3 are safety reads.** At ~18 releases per arm and a measured release-tail
  of 1.5-3 %, an arm expects ~0.3-0.5 tail releases; the gate is therefore P2/P3/
  P4/P5/P6, and P1's M2 share is reported with that exposure. **No rate is
  claimed** — the counts are of a deterministic branch.
* **The supply is controlled** (M1b: identical planned-x sequences), so the only
  difference between C and O is the physical spawn x. That is what makes the A/B
  interpretable despite the branch moving.

## 8. Cost, discipline, and what would stop it

* **Cost**: the two live probes (seed 5, and the pear) ~6 min, M1's two probe runs
  ~4 min, M2/M3's four acceptance-shape runs ~12 min, M4 ~3 min, the two gates and
  `selfcheck.sh` ~2 min. One claim, ~30 min of wall.
* **Discipline**: one claim at a time; the probe and the battery in one session;
  every run through `scripts/154_claim_run.sh`; no `configs/` change unless P5
  fires an adoption (phase 3); the knob default-off and the unset path
  byte-identical.
* **Stop conditions that are not falsifiers**: a renderer wedge in M2/M3 (retry
  once, as P41 did); a claim-script overlap (re-queue); an M1 table miss (fix the
  signature, do not touch the battery).
* **Out of scope, named**: the patch/bed pair-separation question (§2's scope
  gate); the direct/policy interface (`rl_env.select_target`'s x is the *delivered*
  one, so a compensated spawn benefits it for free, but its A/B is its own
  pre-registration — the P43-style interface change re-baselines every direct
  number); a geometry-only (zero-sim) predictor, which §11 of the measurement
  says does not exist yet.
